# Audit of 0.2.0

Security, credentials, compatibility, optimization and interface review of
version 0.2.0, done in phases (see the
[roadmap](../roadmap.md#post-020-program-decided-on-2026-11-16)). This file
grows with each phase.

| Part | Scope | Status |
|---|---|---|
| 1 | Credentials, private data, supply chain | done (2026-11-16) |
| 2 | Privilege boundaries (helper, sandbox, VICI, gateway, webview, installer, scripts, CI) | done (2026-11-16) |
| 3 | Compatibility across distributions | done (2026-11-17) |

Rules followed: no real credential, profile or VPN log was read; dynamic
tests ran only against the test gateway with fake credentials; scans printed
files and counts, never the matched text.

## Summary of part 1

- **No credential leak.** The PSK and the password exist only in memory: of
  the app or CLI while connecting, and of charon during the session. They
  were found in no file, process command line or environment, journal entry,
  unit property, CLI output or exported profile.
- **One real privacy flaw, fixed (A1):** the XAuth username went out unmasked
  in the log, including in "Copy anonymized", whenever the process reading
  the log did not have the credentials.
- **One hardening gap, fixed (A2):** a crash could leave a core dump with the
  credentials on disk.
- **One repository leftover (A0):** the old `v0.1.1` tag on the remote still
  points to the history from before the email rewrite. The maintainer deletes
  it.
- **One strategic risk (P1):** upstream strongSwan disabled IKEv1 by default
  in 6.1.0 and announced its removal. The app exists for IKEv1 VPNs.
- Nothing critical or high in the published 0.2.0. The fixes are on `main`
  and go out with the next release; A1 and A2 change the network component,
  so users will need "Update" in the app.

## Method of part 1

- **Static:** every `expose_secret` call site, every `Debug`/`Serialize` of a
  type holding a secret, every logging call, the command DTOs, the CLI
  prompt, the credentials dialog and the keyring store were read.
- **Dynamic, the canary sweep** (`tests/systemd/inside.sh`, now a permanent
  scenario of `npm run test:systemd`): in a container with real systemd,
  helper and polkit, a user connects to the test gateway. While connected and
  after disconnecting, the test PSK, password and username are searched for
  in every regular file of the system, in every process command line and
  environment, in the journal, in the unit properties, in the CLI output
  (`status`, `logs`, `logs --anonymize`, `profiles show`) and in the exported
  profile. The sweep found A1 and A2; it passes with the fixes.
- **Supply chain:** `npm audit`, `cargo deny`, pinning review, upstream
  advisories (strongSwan, Tauri), gitleaks, hardening flags with `readelf`.

# Part 2: privilege boundaries

Every place where a less trusted side talks to a more trusted one was
reviewed: local user → helper (root), session owner → charon (root, through
VICI), gateway and network → client, webview → Rust commands, user → installer
(`pkexec`), files and scripts, CI and release.

## Summary of part 2

- **No way to root was found.** The ADR-0019 attack was repeated and stays
  blocked; nothing else that a VICI client sends makes charon run a command.
- **Two flaws at the helper boundary, fixed.** A user of the active session
  could make root **delete another program's network interface** (B1), and a
  user who connected after another one **received the end of that session's
  log** (B2). Both need a local account on the same computer; neither is
  reachable from the network.
- **One flaw at the gateway boundary, fixed (B6):** text sent by the gateway
  reached the user's terminal raw.
- **One window in the installation, closed for `.rpm`/`.deb` (B7):** root no
  longer executes a file that the user could swap.
- Smaller hardening: a slow client could hold the helper (B3), the polkit
  check trusted a pid that could have been reused (B4), the helper unit had
  no syscall filter (B5), and two input limits on the client side (B8, B9).
- **Decisions for the maintainer:** refusing IKE initiations from the network
  (P8) needs a test on the real VPN; the rest are small follow-ups.
- The fixes are on `main`, not released. B1 to B5 change the network
  component: users will need "Update" in the app.

## Findings of part 2

### Fixed

| Id | Severity | Boundary | Finding | Fix |
|---|---|---|---|---|
| B1 | Medium | user → helper | **Root deletes an interface chosen by the client.** The `start` request accepted any interface name with the kernel's character set, and the engine, before creating the session interface, deletes the one with that name and reverts its DNS (`ip link del`, `resolvectl revert`). Any user of the active local session could ask for `docker0`, `virbr0`, `wg0` or a bridge and have it removed, or have the DNS of the physical interface reset. No password, no escalation: damage to the computer's network. Present since 0.1.0 | The protocol accepts only `ipsc<N>`. #### How to test P8 on the real VPN

The question is one: **does the gateway ever start a negotiation towards the
client?** It would only do that to renew phase 1 (the IKE SA) when its own
lifetime runs out before the client renews. If it never does, `initiator_only`
changes nothing for this VPN and can be turned on.

Step 1 answers it without changing anything. Step 2 confirms it with the
option on.

1. **Look, with the app as it is.**
   1. Connect as usual and note the time.
   2. See when the client itself will renew phase 1:
      ```bash
      ipsec-client-cli logs -n 500 | grep -E "scheduling re|maximum IKE_SA lifetime"
      ```
      A line such as `scheduling rekeying in 83189s` means the client renews
      after about 23 hours.
   3. Stay connected for longer than the **gateway's** phase 1 lifetime. Ask
      IT for it ("phase 1 key lifetime"); FortiGate's default is 86400 s
      (24 hours). If the VPN is never kept up that long, use the longest
      session that really happens: what cannot occur in real use does not
      need to pass.
   4. Count the negotiations that the gateway started, in the system journal
      (administrator):
      ```bash
      sudo journalctl -u ipsec-client-engine --since "3 days ago" | grep -c "is initiating a"
      ```
      charon writes `<address> is initiating a Aggressive Mode IKE_SA` (or
      `Main Mode`) only when the **other side** starts. Negotiations started
      by the client read `initiating Aggressive Mode IKE_SA ... to <address>`
      and are not counted.
   - **`0`** after a session longer than the gateway's lifetime: the gateway
     does not start negotiations. Go to step 2.
   - **`1` or more:** the gateway renews phase 1 by itself. Do not turn
     `initiator_only` on; P8 is closed as "not applicable to this gateway".
2. **Confirm with the option on.**
   1. Disconnect, and add the option to the engine configuration
      (administrator):
      ```bash
      sudo sed -i 's/^    install_routes = no$/&\n    initiator_only = yes/' \
          /opt/ipsec-client/engine/etc/strongswan.d/zz-ipsec-client.conf
      grep -n "initiator_only" /opt/ipsec-client/engine/etc/strongswan.d/zz-ipsec-client.conf
      ```
      The second command must print one line. The engine reads the file on
      every connection.
   2. Connect and stay connected as long as in step 1.
   3. At the end, the tunnel must still carry traffic: `ipsec-client-cli
      status` shows it connected, and something inside the VPN answers (a
      `ping`, the remote desktop).
   - **Still up:** tell the result; `initiator_only = yes` goes into the next
     release.
   - **It dropped** around the lifetime: the gateway needed to renew. Undo it.
3. **To undo** (or after the test): System → Network component → Reinstall in
   the app, or
   ```bash
   sudo sed -i '/^    initiator_only = yes$/d' \
       /opt/ipsec-client/engine/etc/strongswan.d/zz-ipsec-client.conf
   ```

None of these commands shows credentials. The journal lines do contain the
gateway address: count them (`grep -c`), do not paste them.

## Part 2: what was checked and found sound

| Boundary | Result |
|---|---|
| Helper protocol | One JSON line per connection, 64 KiB limit, unknown fields and operations refused; the client sends numbers, a profile id and DNS values, never a path or a command. Every argument reaches `systemd-run` as `--property=`/`--setenv=` in a single argument, with validated character sets: no injection, no specifier expansion |
| Helper authorization | Identity from `SO_PEERCRED`; every request except `ping` goes through polkit; `stop` and `logs` only for the session owner; `status` hides another user's profile |

In the strongSwan 6.1.0 source, the only command executions in this build are the `updown` (forced), the start/stop scripts (root's configuration only) and `addr2line` when charon prints a crash backtrace (fixed `PATH`). No fetcher, PKCS#11, `resolve` or `ext-auth` plugin is built |
| Gateway → client | Everything the `updown` receives from charon (networks, virtual IP, DNS, peer) is validated again before use; arguments come from a root-owned file, never through a shell; identities are sanitized by charon before logging |
| Webview → Rust | 18 commands, all with typed input. Profile ids are validated before becoming a file name. File paths never reach the webview: the dialogs and drag and drop are handled in Rust, with single-use tokens. Capabilities: `core:default` only (the dialog plugin is not granted to the webview). CSP `script-src 'self'`, no devtools in release, no links or injected HTML in the frontend |
| Installer | Hashes checked on a root-only copy; links, special files and tarball paths outside the engine directory are refused; `pkexec` gets a clean environment; removal only runs the root-owned installer after checking the owners above it |
| Profiles on disk | Directory `0700`, files `0600`, atomic write (temporary file + rename), size limit, strict id format |
| CI and release | `pull_request` trigger only (never `pull_request_target`), `contents: read`, no secrets, actions pinned by SHA, checkout without persisted credentials |

## Method of part 2

- **Static:** the protocol, the helper, the unit files, the entrypoint and the
  `updown`, the installer and its client, the 18 Tauri commands with their
  configuration, the CI workflow and the release scripts were read looking
  for the checks listed in the roadmap for each boundary.
- **strongSwan source:** the 6.1.0 tarball (same SHA-256 as the build) was

  interface names, a foreign `ipsc0`. The dripping-client scenario caught a
  deadlock in the first version of the B3 fix, before it was merged.
- Not done here, and why: P8 on the real VPN (the maintainer's test).

# Part 3: compatibility

Does what is published install and work on the distributions people use?
Checked with two automatic harnesses, kept as permanent tests, plus probes of
the RHEL family.

## Summary of part 3

- **The VPN engine works on all seven distributions** of the matrix, with
  each one's own systemd (249 to 262), polkit (0.105 to 128), iproute2,
  bash and glibc: installer, sandbox, tunnel, routes, DNS, two users, the
  ADR-0019 attack and authorization by the real polkit.
- **The published packages install everywhere they are meant to, but miss
  dependencies (C1):** on a clean system, `pkexec` and `ip` were not brought
  along, so the network component could not be installed or the VPN could
  not start. Fixed: the test packages of this phase bring everything on all
  seven.
- **Image-based distributions could not install the network component**
  (C2, C3): a read-only policy directory, and `/opt` as a link that tar
  replaced.
- **The diagnostics hid a missing systemd-resolved** (C4), the usual case on
  Debian and openSUSE, where the VPN DNS then silently does not work.
- **The RHEL family was documented wrong (C6):** version 9 cannot run the
  app at all, and version 10 needs EPEL. With EPEL, AlmaLinux 10 passes the
  whole matrix and is now part of it.
- Smaller: the language of the tray and notifications (C5), the release
  check of glibc (C7), the helper with no capability at all (C8), and the
  release build writing over published packages (C9).
- Not testable in containers: the graphical desktop (P15).

## Findings of part 3

### Fixed

| Id | Severity | Finding | Fix |
|---|---|---|---|
| C1 | Medium | **Undeclared dependencies.** The packages declared only WebKitGTK, GTK and the tray library. On a clean installation, `pkexec` (needed to install the network component) and `ip` (needed by the engine) were missing on every distribution, and on Fedora and openSUSE also `systemctl`, `systemd-run`, `journalctl`, `find` and `awk`; `libdbus` was linked but not declared. Desktop installations usually have them, which is why it went unnoticed | `.deb`: `libdbus-1-3`, `pkexec`, `iproute2`, `systemd`. `.rpm`: `libdbus-1.so.3()(64bit)`, `/usr/bin/pkexec` (a package of its own on openSUSE, part of `polkit` on Fedora), `iproute`, `systemd`, `findutils`, `gawk`, `tar`, `gzip`. The diagnostics check `ip` when the embedded engine is installed (the AppImage cannot declare it). Test: `tests/compat/packages.sh` fails when a tool is missing |
| C2 | Medium | **Image-based systems: read-only policy directory.** On Fedora Silverblue/Kinoite and openSUSE MicroOS, `/usr/share/polkit-1/actions` cannot be written. The installer stopped there, with the files already in `/opt` and the units in `/etc` but the socket not enabled | The policy goes to `/etc/polkit-1/actions` when the usual directory is read-only, which polkit 124 and newer read; with an older polkit, the installer stops before installing anything and says why. Test: `test:packaging` (read-only directory; polkit 0.105, 122, 124 and 127) |
| C3 | Medium | **Image-based systems: `/opt` replaced.** On Fedora Atomic, `/opt` is a link to `var/opt`. GNU tar, extracting the engine, replaced the link with a real directory: what had been installed through the link vanished and the installation failed (on a read-only root, the extraction itself fails). Found by the C2 test | `tar --keep-directory-symlink`. Since tar now keeps links, the installer refuses an engine tarball with anything but files and directories. Test: `test:packaging` (`/opt` → `var/opt`; tarball with a link) |
| C4 | Low | **The diagnostics hid a stopped systemd-resolved.** They looked for files in `/run/systemd/resolve`, which stay after the service stops, the socket included. With systemd-resolved stopped, "System → Diagnostics" said "active" and the VPN DNS was not applied | The diagnostics make a Varlink call to systemd-resolved and require an answer. A connection is not enough: on systemd 261 and 262 the socket belongs to systemd (socket activation), which accepts the connection and drops it when the service cannot start. The first version of this fix only connected, and the matrix caught it on Fedora and openSUSE. Tests: unit (the four cases seen: answer, error answer from systemd 249, dropped connection, nobody listening); a scenario in the matrix without systemd-resolved: the warning shows, the tunnel works by IP, the log says the DNS was not applied |
| C5 | Low | **Language of the tray and notifications.** The Rust side read only `LC_ALL`, `LC_MESSAGES` and `LANG`; gettext programs also follow `LANGUAGE`, which Ubuntu sets for the chosen language. A user with `LANG=en_US.UTF-8` and `LANGUAGE=pt_BR` got the tray and notifications in English. `pt_PT@euro` was not recognized | `LANGUAGE` first, unless the locale is `C`/`POSIX` (the gettext rule); `pt@…` recognized. Test: unit |
| C6 | Info (documentation) | **The RHEL family was documented wrong.** The installation guide and the README recommended the `.rpm` for RHEL, Rocky and AlmaLinux, without a version. Version 9 cannot run the app at all (see the table above), and version 10 only with EPEL | The documentation lists the tested distributions, says version 9 is not supported, and shows how to enable EPEL on version 10. AlmaLinux 10 joined the matrix (`packages.sh` enables EPEL for the RHEL family) |
| C7 | Info (release) | `verify-release.sh` promised that the AppImage does not need a glibc newer than Ubuntu 22.04's, but read only the app's executable (2.34). The bundled libraries are what need 2.35. The promise held, because everything comes from Ubuntu 22.04, but nothing checked it | Every ELF file in the AppImage is read |
| C8 | Hardening | The helper unit kept `CAP_CHOWN` and `CAP_DAC_READ_SEARCH` (P12 of part 2) | `CapabilityBoundingSet=` (none). The matrix passes on all seven with it, including the real polkit check, which reads the client's `/proc` entries |
| C9 | Info (process) | A release build of `HEAD` wrote to `target/release-artifacts/<version>`, over the published packages of that version | Only the version tag goes there; anything else goes to `<version>-dev-<commit>` |

| Id | Severity | Finding | Proposal |
|---|---|---|---|

| Id | What | Why it is accepted |

| I8 | systemd-resolved is not a dependency: on Debian and openSUSE the VPN DNS needs the user to install it | Installing it changes who resolves names on the whole system. The diagnostics now say it, and the installation guide shows how |

## Method of part 3

- **Systemd test on each distribution:** `tests/systemd` with the base image
  of each distribution, pinned by digest in `tests/compat/distros.txt`, and
  the helper and the CLI built in the release image. A last scenario removes
  the uid list and talks to the real polkit.
- **Packages:** `tests/compat/packages.sh` installs the `.deb`/`.rpm` with
  `apt`, `dnf` or `zypper` in a clean container, as an update from an older
  version, and checks libraries, startup, hashes and tools.
- **Binaries:** `objdump -T` over the app, the helper, charon and every ELF
  file inside the AppImage.
- **RHEL family:** the `.rpm` installed by `dnf` on AlmaLinux 9 and 10, with
  and without EPEL; AlmaLinux 10 then joined the matrix.
- **Locale:** the gettext rules for `LANGUAGE`, `LC_*` and `C`, unit tested.
- Two fixes of the harness itself: the Ubuntu 24.04 image comes with a user
  on uid 1000, and `pkaction` 0.105 exits with 1 even when it finds the
  action.
