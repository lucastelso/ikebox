# Audit of 0.2.0

Security, credentials, compatibility, optimization and interface review of
version 0.2.0, done in phases (see the
[roadmap](../roadmap.md#post-020-program-decided-on-2026-11-16)). This file
grows with each phase.

| Part | Scope | Status |
|---|---|---|
| 1 | Credentials, private data, supply chain | done (2026-11-16) |
| 2 | Privilege boundaries (helper, sandbox, VICI, gateway, webview, installer, scripts, CI) | pending |
| 3 | Compatibility across distributions | pending |

Rules followed: no real credential, profile or VPN log was read; dynamic
tests ran only against the test gateway with fake credentials; scans printed
files and counts, never the matched text.

## Summary of part 1

- **No credential leak.** The PSK and the password exist only in memory: of
  the app or CLI while connecting, and of charon during the session. They
  were found in no file, process command line or environment, journal entry,
  unit property, CLI output or exported profile.
- **One real privacy flaw, fixed (A1):** the XAuth username went out unmasked
  in the log, including in "Copy anonymized", whenever the process reading
  the log did not have the credentials.
- **One hardening gap, fixed (A2):** a crash could leave a core dump with the
  credentials on disk.
- **One repository leftover (A0):** the old `v0.1.1` tag on the remote still
  points to the history from before the email rewrite. The maintainer deletes
  it.
- **One strategic risk (P1):** upstream strongSwan disabled IKEv1 by default
  in 6.1.0 and announced its removal. The app exists for IKEv1 VPNs.
- Nothing critical or high in the published 0.2.0. The fixes are on `main`
  and go out with the next release; A1 and A2 change the network component,
  so users will need "Update" in the app.

## Findings

Severity: how bad it is if it happens, for this app's threat model
([SECURITY.md](../../SECURITY.md)).

### Fixed

| Id | Severity | Finding | Fix |
|---|---|---|---|
| A0 | Medium (privacy, repository) | The `v0.1.1` tag was pushed before the commit email rewrite. A force push does not delete a tag that no longer exists locally, so the remote tag kept the whole old history reachable, with the personal email in every commit | Local tag deleted; all local branches, tags and remote-tracking refs checked (noreply only). **Pending with the maintainer:** `git push origin :refs/tags/v0.1.1`. The old commits stay reachable by hash until GitHub Support purges them |
| A1 | Medium (privacy) | **XAuth username unmasked in logs.** The masking replaced only identities the process already knew. The username comes from the credentials, so when they were not in the keyring (connection without "remember") and another process read the log, it was shown raw: `ipsec-client-cli logs`, `logs --anonymize`, the app's log panel after reopening with the VPN up, and **"Copy anonymized"**, the text meant for bug reports. A gateway identity that is not in the profile leaked the same way. Present since 0.1.0 (log) and 0.2.0 (anonymized copy) | `fix/mask-unknown-identities`: identities are also masked by the shape of the charon line: quoted (`'%Y'`, `"%Y"`), in brackets after an address (`%H[%Y]`) and in the log level 2 configuration dump (`xauth_id = %Y`). Values that are not identities (plugin, config, interface, file) stay readable. Unit tests with no known identity; covered end to end by the canary sweep |
| A2 | Low | **No core dump protection.** The app and the CLI hold the PSK and the password while connecting; charon holds them and the session keys. `systemd-coredump` keeps the memory of a crashed process on disk for days, against ADR-0007 | `fix/no-core-dumps`: `RLIMIT_CORE=0` at startup in the app and the CLI (inherited by the webview processes, where the password is typed); `LimitCORE=0` in the engine transient unit and in the helper unit. Tests: unit (limit applied), `test:systemd` (unit properties) |

### Proposed (need a decision or belong to a later phase)

| Id | Severity | Finding | Proposal |
|---|---|---|---|
| P1 | Strategic | **Upstream is removing IKEv1.** strongSwan 6.1.0 disables IKEv1 by default (we build with `--enable-ikev1`, so it works, and charon logs a deprecation warning) and announces its removal "in a future release, likely within the next year". Every profile this app supports today is IKEv1 | Decide in an ADR (amending ADR-0016): stay on the last release with IKEv1 and apply upstream security patches ourselves (they are published per CVE), and evaluate what that maintenance costs; follow the upstream advisories on a schedule. Until then, do not upgrade past the last release with IKEv1 without that decision |
| P2 | Low | With "remember" checked, the credentials are stored in the keyring **before** the connection succeeds: a mistyped password is stored | Store only after the connection is established |
| P3 | Low | Two Tauri advisories of mid-2026 (CSP nonce bypass through `data:`/`blob:` script sources; dialog plugin granting recursive directory access) could not be confirmed on the primary source, so the fixed versions are unknown. Their preconditions do not hold here: `script-src 'self'` only, the webview loads only bundled content, and the dialog plugin is not granted to the webview (the file picker is opened from Rust). `cargo deny` reports no advisory for the locked versions | Update to tauri 2.12.6 and `@tauri-apps/api`/`cli` 2.12.5 (available), with a GUI smoke test by the maintainer |
| P4 | Low | The release build image verifies `rustup-init` and the Node.js tarball against checksums downloaded from the same server, which catches corruption but not a compromised server | Pin the expected SHA-256 of both in the Dockerfile, as is done for strongSwan |
| P5 | Info | GMP is linked statically into the engine from the Ubuntu 22.04 package: a GMP fix needs an engine rebuild, and the version is not recorded | Record the GMP version in `BUILDINFO` and check it in `verify-release.sh` |
| P6 | Info (part 2) | The release app honours `IPSEC_CLIENT_COMPONENT_BUNDLE` (where the component bundle comes from) and `IPSEC_CLIENT_HELPER_SOCKET` | Review in part 2: restrict them to debug builds |
| P7 | Info (phase 4) | The engine tarball ships `swanctl` and strongSwan's stock `_updown`, not used in production | Remove them from the bundle (tests can use their own copy) |

### Accepted (inherent or by design)

| Id | What | Why it is accepted |
|---|---|---|
| I1 | Other local users can see that a VPN is up, its virtual IP and routes, and the DNS servers and domains (`resolvectl status`). `systemctl show ipsec-client-engine` shows the same DNS data, the profile id and the owner's uid | Linux exposes network state to every local user; none of it is a secret. The engine log and the VICI socket are restricted to the session owner |
| I2 | The system journal keeps the raw charon log (username, group id, gateway) | Only root and the journal groups (`adm`, `wheel`, `systemd-journal`) read it. The helper gives the log only to the session owner, and the app masks it on display |
| I3 | Strings typed in the webview and the IPC buffers cannot be zeroed | They are not stored anywhere (dialog state is cleared on submit and on close; no `localStorage`, console or URL), and A2 keeps them out of core dumps |

## What was checked and found sound

| Area | Result |
|---|---|
| Secret types | `Credentials`, `SharedSecret`, VICI `Message` values and frames are zeroed on drop; `Debug` is redacted on all of them |
| Logging | No `tracing`/`eprintln!` call receives a secret. The helper logs only the request kind and the profile id |
| CLI | Credentials come only from the TTY prompt or stdin; no argument or environment variable carries a secret |
| App commands | Typed credentials move into `SecretString` without a copy; errors carry no secret |
| Frontend | Dialog state cleared on submit and close; `localStorage` holds only theme, language and the selected profile id; no `console.*` |
| Keyring | Secret Service through an encrypted D-Bus session; one item per profile and field; `forget` removes all three |
| charon log level | Capped at 2 in the protocol and in the entrypoint (key material needs level 4) |
| Dependencies | `npm audit`: 0 vulnerabilities (production and development). `cargo deny`: advisories, bans, licenses and sources ok |
| Pinning | 11/11 GitHub Actions by commit SHA, `contents: read`; every base image by digest; strongSwan by SHA-256 and GPG signature |
| strongSwan | 6.1.0 is the latest release and fixes the eleven CVEs of September 2026 (none in the code paths of an IKEv1 PSK + XAuth client except the logging memory leak, fixed) |
| Shipped binaries | App, helper, charon, swanctl: PIE, full RELRO, non-executable stack; charon with stack protector and `FORTIFY_SOURCE`; no setuid, no world-writable file, no RPATH; glibc ≤ 2.34 |
| Repository | `check-private.sh --tracked` and `--history` clean; gitleaks 8.30.1 over all 63 non-merge commits: no leaks |
| Release packages | `check-private.sh --artifacts` clean on the 0.2.0 packages; the maintainer's private profile values were counted inside them: zero occurrences of every identifying field |

## Method

- **Static:** every `expose_secret` call site, every `Debug`/`Serialize` of a
  type holding a secret, every logging call, the command DTOs, the CLI
  prompt, the credentials dialog and the keyring store were read.
- **Dynamic, the canary sweep** (`tests/systemd/inside.sh`, now a permanent
  scenario of `npm run test:systemd`): in a container with real systemd,
  helper and polkit, a user connects to the test gateway. While connected and
  after disconnecting, the test PSK, password and username are searched for
  in every regular file of the system, in every process command line and
  environment, in the journal, in the unit properties, in the CLI output
  (`status`, `logs`, `logs --anonymize`, `profiles show`) and in the exported
  profile. The sweep found A1 and A2; it passes with the fixes.
- **Supply chain:** `npm audit`, `cargo deny`, pinning review, upstream
  advisories (strongSwan, Tauri), gitleaks, hardening flags with `readelf`.
