# Third-party notices

Ikebox is licensed under GPL-3.0-or-later (see `LICENSE` and
ADR-0017). It distributes or depends on the components below, under their own
licenses.

Every package carries the texts in `/usr/lib/ikebox/licenses/`: this
file, the project's `LICENSE`, `THIRD_PARTY_LICENSES.txt` (the crates and npm
packages compiled into the app, the CLI and the helper, generated by
`scripts/third-party-licenses.mjs`) and `engine/` (strongSwan, OpenSSL, musl).
Each release attaches `ikebox-<version>-sources.tar`, the
corresponding source of the embedded engine (`scripts/release-sources.sh`).

## Embedded engine (distributed compiled inside the app)

### strongSwan

- **License:** GPL-2.0-or-later, with an exception for combining with LGPL
  libraries and OpenSSL. The des, md4 and md5 plugins have their own
  permissive terms. The full texts go in the engine package, in
  `opt/ikebox/engine/share/licenses/strongswan/`.
- **Corresponding source code:**
  - the official tarball at <https://download.strongswan.org/>, with the
    version and SHA-256 pinned in `native-engine/versions.txt` and the GPG
    signature checked in the build (key in `native-engine/keys/`);
  - **two modifications** by Ikebox, in `native-engine/patches/`:
    - `0001-vici-forced-updown-if-id.patch` (2026-11-16) changes
      `src/libcharon/plugins/vici/vici_config.c` so that charon ignores the
      `updown` and the `if_id` sent by the VICI client when
      `charon.plugins.vici.force_updown`/`force_if_id` are set (ADR-0019);
    - `0002-vici-no-credential-paths.patch` (2026-11-17) changes
      `vici_config.c` and `vici_authority.c` so that, in that same mode, the
      VICI client cannot name a certificate by file path or token.

    The build applies the patches over the official tarball and records the
    SHA-256 of each one in the package `BUILDINFO`;
  - the build options are in `native-engine/build/build-strongswan.sh` and in
    the package `BUILDINFO`.

### OpenSSL (libcrypto)

- **License:** Apache-2.0. The text goes in the engine package, in
  `opt/ikebox/engine/share/licenses/openssl/` (from
  `native-engine/licenses/`). strongSwan's license carries an exception for
  combining it with OpenSSL; the combination is distributed under the GPL
  version 3 terms that strongSwan's "or later" allows, which Apache-2.0 is
  compatible with (ADR-0027).
- **Use:** statically linked into charon (`openssl` plugin: RSA, ECDSA, the
  MODP and ECP DH groups; ADR-0027). Until 0.9.0, GMP did the MODP groups
  and RSA.
- **Corresponding source code:** OpenSSL 3.5.9 as packaged by Alpine
  (`3.5.9-r0`, recorded in `BUILDINFO`): the upstream release
  (<https://openssl-library.org/>) and Alpine's packaging at aports commit
  [`29b9ec24`](https://gitlab.alpinelinux.org/alpine/aports/-/tree/29b9ec24b1b5b39aeef51fa2a044210e2ec5258e/main/openssl),
  both in the release's sources archive. To rebuild, use
  `native-engine/build.sh`.
- **Engines built on a host** (`native-engine/build.sh --host`, ADR-0032),
  not the project's packages: they record their own OpenSSL and musl in
  `BUILDINFO`. When the toolchain has no static OpenSSL, it is the upstream
  release pinned in `native-engine/openssl.txt` (3.5.9, the same as the
  builder's), compiled unchanged.

### musl libc

- **License:** MIT. The text goes in the engine package, in
  `opt/ikebox/engine/share/licenses/musl/` (from
  `native-engine/licenses/`).
- **Use:** the C library of charon, statically linked (ADR-0020).
- **Corresponding source code:** musl 1.2.6 as packaged by Alpine
  (`1.2.6-r3`, recorded in `BUILDINFO`): the upstream release
  (<https://musl.libc.org/>) and Alpine's packaging at aports commit
  [`8f79d393`](https://gitlab.alpinelinux.org/alpine/aports/-/tree/8f79d39391b46d6dbf1800fb68b8212a21d5ee2e/main/musl),
  both in the release's sources archive.

## Docker backend (tests and development)

The `engine/` image is **built locally** from the Debian 13 packages
(strongSwan 6.0.1). The project does not distribute that image, and release
builds of the app have no Docker engine.
